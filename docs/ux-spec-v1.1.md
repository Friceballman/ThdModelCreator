# UX仕様書 ver1.1｜対話によるキャラクター部品制作

作成日：2026-10-19。制作フローver1.0を操作・状態・受け入れ条件へ具体化する。既存の設計書ver1.0は履歴として保持する。本仕様は目標仕様であり、機能の実装完了を意味しない。

## 1. 利用者の基本体験

会話で「この資料から、このキャラクターを作りたい」と依頼できる。Codexが正式な管理CLIを操作し、利用者は対象・保持条件・候補の見た目・採用を判断する。毎回UUIDやコマンドを手入力することを前提にしない。内部操作は追跡可能なID・固定計画で行う。

操作の軸は画像生成ハーネスと同じ、案件→資料のインポートとタグ付け→要件→計画確認・承認→実行→候補比較→選択→名前付き出力。3D固有の部品分割確認、仮組み、形状確定、材質作成・適用を加える。

## 2. 案件・インポート・タグ付け

- 案件を新規作成またはIDで再開し、目的と用途を保持する。暗黙の「現在の案件」に依存しない。
- 画像をPNG/JPEG/WebPとして検証して案件内へ不変コピーする。元ファイルを変更しない。
- タグはrole、view、description、priorityの組合せを基本とする。roleはpose、silhouette、design、face、color、orthographic、part、style、other。priorityは1〜5、1が最高。
- 一枚を複数役割で使う場合は別の参照レコードを作れる。同じ画像だから別の役割も同じと推定しない。
- メタデータ改訂は旧版と理由を残す。実画像の差替えは新規取り込み。
- Codexが実際に画像を読めない場合、インポート成功だけで「全資料を理解済み」と報告しない。

## 3. 要件整理

must_keep、must_change、improveで維持・変更・改善条件を記録する。禁止事項も明確な条件として表現し、部品または全身に対象を関連付ける。実寸や背面の不明点、資料間の矛盾を推測で確定しない。更新・廃止は理由と履歴を残す。

## 4. 部品分割の確認

Codexが部品構成の案を提示し、身体ベース、髪、衣服、装備、持ち物等の分け方と接続方法を利用者が確認する。身体・腕・脚は原則連続したベースとし、細分化しすぎない。

各部品に固有IDを付ける。構成案は版を持ち、明示承認した構成版を生成計画に固定する。構成改訂時は既存部品IDを再利用でき、過去版や候補を削除しない。身体ベースの入手・生成方式や権利条件が不明なら相談する。

## 5. 計画の提示と承認

実行前に案件、対象部品、使用資料、現在の要件、入力の版、実行内容、保持条件、保存先、制約を提示する。計画には不変の入力スナップショットとhashを持たせる。

- planは記録を作るだけで、生成・Blender起動を行わない。
- request-approval→approveで計画内容への承認を記録する。実行開始とは分ける。
- executeは承認済みの計画だけを実行する。コード・入力ファイル・部品構成の変更を無断で取り込まない。
- image_prepareは画像の準備・確認工程。描き起こしには別の画像生成機能と出力の受領が必要で、CLIだけで利用可能とは扱わない。
- geometryは承認した一部品・一画像・一回のTripoSR生成を基本にする。希望候補数を理由に自動反復しない。
- assemblyは使う各部品候補と位置・回転・スケールを固定する。
- surfaceは使う材質の版と適用先を固定する。
- 編集は親候補と対象部品を指定し、局所変形、配置、部品交換、再生成を区別する。

状態はdraft、awaiting_approval、approved、running、succeeded、failed、blocked、cancelled、result_unknown。結果不明時はプロセスと保存先を確認するまで重複実行しない。終端計画を再実行せず、新しい計画で再試行する。保存済み成果物は保持する。

## 6. 部品制作と仮組み

生成用画像を元資料と比較して確認し、TripoSRまたは利用条件を確認した既存資産から形状を得る。部品ごとに対話で修正し、固有IDの下へ新しい形状候補を保持する。

必要部品が揃ったら全身を仮組みし、頭身、サイズ、接続、隙間、重なりを複数方向から確認する。仮の色で部品を識別できるようにする。別部品のまま保持してよい。オブジェクトをまとめることと、表面を縫合することを混同しない。

組み立て後も部品構成を保ち、全身候補には使った部品候補ID・版・配置を固定する。ある部品の新しい版を選択しても、過去の全身候補へ自動反映しない。

## 7. 形状確定とマテリアル

全身を仮組みして必要な接合・軽量化・形状修正を済ませ、利用者が形状をいったん確定する。その後に各部品のUV・詳細な色・模様・粗さ・金属感等を仕上げる。素材の試作や仮の色は早い段階でも可能。

- マテリアルは部品単位で管理・適用し、品質は全身を見ながら判断する。
- 材質にも固有IDと版、適用対象の部品・形状候補を持たせる。
- 最初の実装では、色、Roughness、Metallicの数値からBlenderの標準材質を構築する方式を対象にできる。これはAIによるPBRテクスチャ一式生成とは呼ばない。
- テクスチャ描き起こし、UV、ベイクは対応している処理だけ実行する。未対応は理由と次の操作を示す。
- 形状変更後は影響するUV・材質・ベイク・ウェイトを再確認する。確定済みの過去版は変更せず派生させる。

## 8. レビュー・選択・出力

固定したカメラ・照明で正面、側面、背面、斜めを確認する。構造検査と人の見た目の評価を分け、要件ごとにpass、fail、uncertain、not_applicableと理由を保存する。

候補はpending、selected、on_hold、rejected。複数選択を許し、正式採用は別のset-approvedで全身候補を最大1件指定する。正式採用と生成成功を混同しない。

通常出力はselectedの全身候補すべて。途中の画像・部品は混ぜない。名前指定、1件は連番なし・複数は候補ID順に_001からの連番とし、日本語・空白を許可する。禁止名・パス・上書きを拒否する。

source出力は編集原本・モデル・プレビュー・検査・材質情報等を同梱し、manifestから出所候補とhashを追跡できるようにする。実行ごとに新規出力IDへ保存する。UE・リグ・動作が未確認なら、その事実を出力に明記する。

## 9. 再開とエラーの案内

statusは保存済み状態から次の操作を日本語で示す。生成失敗、入力不足、部品構成未承認、形状未確定、材質不足を区別する。入力不備を黙って補正したり、失敗を成功表示したりしない。

案件データの更新はCLIを通し、ロックと原子的保存で既存状態を保全する。未知schema、hash不一致、案件外パス、残存ロックは拒否する。運用データの場当たり的な直接編集を推奨しない。

一覧は完全なIDと説明を省略せず表示する。初期実装は端末全文・JSON出力を先に提供し、対話端末のVS Code一覧表示・専用キャッシュは後続とする。未実装の表示経路をhelpや報告で利用可能としない。

## 10. 実装の進め方

Python 3.11以上の管理コアとCLIを用い、TripoSRの既存仮想環境やBlender内蔵Pythonと分離する。初期呼出しはインストール不要のローカルランチャーも用意する。既存環境の依存を変更しない。

1. 案件・画像インポート・タグ・要件・部品分割確認・固定計画・承認・状態案内を実装する。
2. 既存部品取り込みとTripoSR／Blenderのアダプタ、仮組み・限定編集・形状確定を接続する。
3. 標準材質の作成・版管理・適用と全身候補の比較・選択・source出力を実装する。
4. 画像の描き起こし・UV・ベイク・高度な編集・UE・動作を検証しながら追加する。

最初の保存方式は案件単位のJSON文書と不変の成果物ディレクトリを用いる。計画・候補・参照等のIDはUUIDで独立させ、プロジェクト文書内の索引で関連付ける。複数JSONの同時更新を避けるための初期実装上の具体化であり、過去の案件データの移行が発生したとは扱わない。

実生成を自動テストから暗黙に開始しない。実機試験は承認した範囲で行い、処理時間と未検証事項を記録する。コミット・push・システム変更は今回の開始依頼に含めて自動実行しない。

## 11. 受け入れ条件

- UX-01：案件を作成・再開し、元画像を変えずに複数資料を役割・方向・優先度付きで登録できる。
- UX-02：要件と理由・改訂履歴を保持し、計画作成後の更新で過去計画が変わらない。
- UX-03：部品構成を提示・改訂・承認し、固有部品IDを維持できる。
- UX-04：計画作成・承認と実行を分離し、未承認・hash変更・重複実行を拒否できる。
- UX-05：画像候補・部品候補・全身候補を区別し、全身の構成が後から変わらない。
- UX-06：仮組みを確認し、形状確定後に材質を仕上げる順序を案内できる。
- UX-07：材質の作成・版・適用先を追跡し、元候補を上書きせず全身へ適用できる。
- UX-08：比較・レビュー・選択・正式採用を区別し、名前付きsource出力の依存とhashを検証できる。
- UX-09：別の会話から状態・次の操作を復元し、未対応機能を明示できる。
- UX-10：既存TripoSR環境を変更せずに呼び出し、失敗時に元資料・候補を保全できる。

## 14. 実用試験に向けた追加方針（2026-10-19）

利用者の確認を受け、検証対象と合格基準は案件ごとに定義する。上記UX-01〜10はハーネスの機能条件であり、個別キャラクターの造形合格基準を固定するものではない。案件の要件とレビューへ対象・用途・合否の理由を記録する。

身体ベース候補としてMakeHuman公式HM08メッシュをCC0の資産として確保した。上流版とライセンス原文を保存し、補助形状を除いた身体OBJ・.blendを用意する。身長1.7mは取り回しの仮寸法で、案件の体型・頭身・ポーズに合うかは都度確認する。候補確保と案件での正式採用は別。リグ・UEは未検証。

生成用画像も部品と同じく、元資料・親画像→作成／編集計画→承認→外部処理→画像候補保持→比較・ユーザー確認→入力承認という反復フローを持つ。画像登録だけでは入力承認しない。geometry計画では承認された画像候補とファイルhashを固定する。画像準備アダプタの自動実行は未実装だが、承認済みimage_prepare計画への外部結果登録と親候補の追跡を実装した。

見た目は、ユーザーが候補の.blendをBlenderで都度確認する運用を認める。独自の高機能ビューアを実用試験の必須条件にはしない。確認対象IDと結果をレビューに残し、候補の直接上書きは避ける。

復旧はCodexに委ねる。別の会話から案件全文・未決事項・承認範囲・親候補・ログ・実体ファイル整合性を読み戻せるよう、project resume、引き継ぎメモ、索引の全文チェックポイントを追加した。結果不明の自動再実行・承認推定・ロック奪取は行わない。詳細はdocs/session-resume.md。

## 15. 画像生成ハーネスに合わせたCLI（2026-10-19）

ユーザーの指示を受け、作成・一覧は案件ID、生成計画や候補等の操作は対象IDだけで指定できる形に揃えた。PowerShellで `. .\mwb.ps1` を一度読み込むと短い `mwb` を使える。永続PATH・既存環境は変更しない。

generate/editのshow・request-approval・approve・execute・register・cancel、candidateのshow・比較・選択、画像入力承認等を対象IDで操作する。通常の承認はIDのみで対象と内容を端末に表示し、yと答えた場合だけ根拠を保存する。hashの手入力を省いても内容hash検証は行い、確認後に変わった計画は拒否する。非対話操作では実際の会話承認を--evidence／--reasonで指定し、証拠のない承認は拒否する。

--promptを説明文の共通指定として追加。部品構成の--name、組み立ての--bindと配置指定、材質の--material、要件単位のreviewにより、通常の制作で利用者がJSONを手作成する必要を減らす。入力画像からgeometryと部品、材質からsurfaceを特定するが、曖昧な対象は選ばない。自然文の解釈はCodexが担い、CLI自身が形状や配置を推論するとは扱わない。

従来の二つのID・--hash・詳細JSONは互換として保持。案件データの移行は不要。操作マニュアルはdocs/operation-manual.mdを現行とし、ver1.0は履歴として残す。
