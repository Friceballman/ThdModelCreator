# 別の会話から案件を再開する

制作案件のフォルダ全体を正本として保持する。Git対象外のprojects、または--rootで指定した保存先をバックアップする。会話履歴だけに決定事項を残さない。

## 通常の再開

1. このリポジトリのAGENTS.md、docs/user-guide.md、仕様を読む。
2. `mwb.py --json project list` で案件を特定する。別保存先なら共通引数 `--root <保存先>` を付ける。
3. `mwb.py --json project resume <案件ID>` を読む。案件全文、要件と改訂、部品構成、計画と承認根拠、画像・形状・材質の候補と親ID、レビュー・採用・出力、引き継ぎメモ、ファイルのhash検査、保留計画とロック、.blendの所在が得られる。処理の再実行やロック解除は行わない。
4. 承認済み計画の範囲と、ユーザーの次の依頼を照合する。資料・画像・候補を実際に参照する。ユーザーは記載の.blendを開いて確認してよい。
5. 未決事項は未決のまま説明し、過去の成功や会話の推測を正式採用・新規生成の承認に読み替えない。

決定・未決事項・次の作業は `project note <案件ID> --kind decision|open_question|next_step --text <内容>` で保存する。新しい判断が古いメモを置き換える場合は、対象メモIDと置き換える理由を本文に記す。ログには個人情報や秘密情報を不要に含めない。

## 中断・破損時にCodexが行うこと

- まず元の案件フォルダを保全する。resumeは読み取り専用で、異常を見つけても自動修復しない。
- running/result_unknownやロックが残っていれば、記録されたPIDだけで断定せず、プロセスのコマンドライン・開始時刻・該当runのログと出力を照合する。稼働中の処理を重複実行しない。
- `runs/<run-id>/plan.json` に開始時の計画、同じ場所に実行ログ・job・出力がある。未登録ファイルを成功した候補と推定して登録しない。候補採用も自動で行わない。
- この更新以降の作成・更新では、`recovery/<UUID>.json` に案件全文の不変チェックポイントを先に保存し、その後project.jsonを原子的に更新する。実行開始時のrunningも保存する。過去案件は次の更新以降に作成され、遡及生成はしない。
- project.jsonが破損してresumeも読めない場合、Codexがrecovery内を検査する。案件ID・schema・events末尾の時刻・要件・計画のhash・参照ファイルとの一致を照合し、候補となる版を別コピーに取り出す。チェックポイントは主索引の更新直前に書くため、主索引より先の未確定版を含む可能性がある。ファイル時刻だけで自動採用しない。
- 復元先を別フォルダに用意し、原本を残して整合性を検証する。復旧根拠・失われた可能性のある更新・未確定の結果を引き継ぎメモへ記録する。完全復元できない資料や承認は推定で埋めない。

チェックポイントは索引の冗長化で、画像・OBJ・.blend等の実体を複製するものではない。フォルダ全体の消失には別途バックアップが必要。ロック解除・状態修復の専用GUIは設けず、Codexが上記の証拠を確認して対応する。
