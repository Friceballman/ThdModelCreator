# 3Dモデル生成ハーネス ver2.0 設計

作成日：2026-10-19。状態：概念設計。実装契約は [仕様書 ver2.0](spec-v2.0.md) を優先する。実装と検証の現状はREADMEを参照する。

本書はユーザーのver1.0実験後の指示を設計へ反映する。対象は単一ユーザーのローカル制作ハーネス。既存の案件管理、資料・要件・部品ID、固定計画、候補、履歴、レビュー、選択、source出力は維持する。制作対象ごとの外観・面数・用途の合格条件は案件の計画で定める。

## 1. 変更の中心

二次元資料から新しい形状を作る経路を、CodexがBlenderを直接操作して造形する方式に統一する。Codexは制作意図、使用資料、推定箇所、構築方法を部品ごとに記録し、保存したモデルを複数方向から見て自己点検する。造形品質の最終判断はユーザーが行う。実機で成功するまでは、この経路を品質保証済みとは表示しない。

外部の3D生成アダプタは置かない。旧案件の記録は保持するが、旧式の造形計画は実行せず、必要な場合はBlender用の新計画を作る。

## 2. ユーザーが関わる場面

通常の制作では、次の場面だけでユーザーの入力・判断を求める。案件立ち上げ、画像インポート、タグ付け、生成計画の作成は一つの会話でまとめて進められる。

1. 案件の目的・用途・成果物の範囲を決める。
2. 元画像をインポートし、資料を視覚的に確認する。
3. 画像の役割、方向、優先度、使う要素・使わない要素を確認する。
4. 一回の制作計画を確認・承認する。計画には部品構成案、制作方法、許可する内部修正範囲、試行回数と処理予算、出力内容、保持条件を含める。
5. 全部品の「造形用資料パック」をまとめて確認・承認する。部品ごとの正面・側面・背面など、寸法・接続位置、配色領域、資料にない部分の推定を提示する。単純な球などでは三面図の代わりに寸法付き構築図を使える。確認済み画像・図面のファイルhashを固定する。
6. 完成した全身候補をBlender原本と複数方向の画像、材質意図、検査結果、未確定事項で確認し、修正箇所・選択・保留・正式採用・出力を指示する。

計画承認と造形用資料パックの承認は異なる。造形用資料パックの承認前には新規造形を始めない。制作中の中間成果はいつでも閲覧できるが、通常は都度の承認要求で作業を止めない。計画の範囲を超える入力・方法の変更、利用条件が不明な資産の採用、根拠のない重要な形状推定が必要になった場合は作業を止め、該当部分をユーザーに示す。沈黙を承認とみなさない。

## 3. 承認と内部計画

ver1.0の `draft → awaiting_approval → approved → running → succeeded / failed / blocked / result_unknown` を維持する。承認の単位として、全体の制作計画（親計画）を追加する。親計画には案件ID、部品構成版、使用元資料と要件版、予定工程、選択した造形方式、許可された局所修正、最大試行回数、保持条件、除外事項を固定する。ユーザーがこの内容を明示承認する。

内部の画像準備、部品造形、仮組み、材質適用は、親計画に紐づく子計画として従来どおりCLIに記録する。子計画の許可根拠には親計画IDと、造形に使う場合は承認済み資料パックIDを記録する。子計画をユーザーが個別に承認したと偽って記録しない。実行前にCLIが親計画の範囲、入力hash、必要な前工程、試行枠を検証する。承認範囲外の子計画は実行を拒否する。生成・再生成はこの明示承認された範囲だけで行う。

親計画の計画時に未作成の資料パックは、作成後にユーザーが内容とhashを確認する。その後の造形子計画は確認済み資料パックの版を入力として固定する。資料パックが変わった場合は、その資料を使う下流計画を作り直す。

## 4. 造形用資料パック

Codexは元資料と矛盾を照合し、部品ごとに造形用資料パックを作る。元資料のコピーは保持し、派生画像が元資料を置き換えない。資料パックには次を記録する。

- 部品ID、名称、役割、親となる資料ID、元画像内の領域、優先順位、保持・変更条件。
- 正面・左右いずれかの側面・背面・斜めなど、必要な方向の参照画像または構築図。画像生成、切り抜き、背景除去、手描き・外部作成を区別する。
- 各方向の整合性、共通の軸と寸法基準、接続先・アンカー、隠れた面や厚みの推定、矛盾と不確実性。
- 形状と分けて、色・模様・材質の参照領域および意図。色の数値化だけで質感が再現できるとは扱わない。

存在しない側面・背面を画像生成で補う場合は「推定」と表示する。正面だけを確定資料、生成した背面を同等の実測資料として扱わない。各方向の資料は由来と推定の有無を個別に管理する。必要な資料が作れず接続や輪郭を決められない場合は、その部品だけ `blocked` とする。

## 5. 部品分解とBlenderでの直接造形

Codexは資料パックに合わせて、低い面数で輪郭・接続・必要な変形を表せる部品構成を立案する。単純形状はプリミティブ、回転体、押し出し、カーブ等で作る。複雑な部位は小さな単位へ分けられるが、曲がる身体を面数削減のためだけに無条件で分割しない。身体・腕・脚の連続性、見える継ぎ目、将来の変形要件を先に確認する。面数は全案件共通の固定上限ではなく、案件の用途・表示距離・部品の役割から親計画に目標を記録する。

CodexがBlender PythonまたはBlender内での手操作を用いてメッシュを制作する。反復できる操作は実行スクリプト、パラメータ、Blender版、入力・出力hash、ログを保存する。手操作を行った場合も作業前後の `.blend`、操作の要旨、変更したオブジェクト・部品IDを記録する。Blender内オブジェクトに部品IDと候補IDを持たせ、案件索引と照合する。元候補は直接上書きしない。

部品ごとの内部手順は、資料パックから輪郭・特徴点・比率を拾う → 最少の部品と面で仮形状を作る → 参照画像と同じ方向・縮尺の画像で比較する → 必要な箇所だけ頂点・輪郭・厚みを調整する → 接続と構造を検査する → 候補として登録する、の順にする。試行ごとに変更理由と比較画像を残し、計画で決めた試行枠を超えて自動反復しない。輪郭を維持できないほどの面数削減は採用しない。

各部品の候補は、編集可能な `.blend`、交換用メッシュ、正面・側面・背面・斜めの画像、検査記録、制作意図、親候補IDを持つ。メッシュの自己点検では、対象の輪郭・寸法・向き・接続、過剰な凹凸・穴・重複、面数、非多様体辺等を調べる。閉じたメッシュが必要かどうかは用途ごとに判断する。Codexは画像と資料を比較して所見と不確実な箇所を記録するが、機械的な検査成功を見た目の合格と同一視しない。

見た目の自己点検は要件ごとに `pass / fail / uncertain / not_applicable` と理由・根拠画像を残す。輪郭、特徴部位、ポーズ、接続、配色、材質を別々に評価し、ユーザーの最終レビューとは別記録にする。「面の陰影を滑らかにする」と「頂点を動かして凹凸を減らす」は別の編集方式として計画・比較・履歴に記載する。既定の確認画像は正面・側面・背面・斜めとし、重複する反対側の確認ファイルは必要な場合だけ作る。

## 6. 仮組み、形状確定、材質

各部品の候補IDと位置・回転・スケールを固定して仮組みし、別オブジェクトのまま全身候補を作る。Codexが配置を提案・調整し、複数方向の画像と `.blend` を確認する。仮組み後のサイズや位置の手動調整を正式に取り込めるようにし、変更前候補・変換値・変更者・理由を残した新しい全身候補にする。オブジェクトの配置と表面の接合は別工程として記録する。

形状・接続をいったん確定してから材質を仕上げる順序を維持する。材質は部品と形状候補に紐づけ、参照画像の領域、狙う色・粗さ・金属感・模様・凹凸、使用ノード・テクスチャの由来、実際の適用先を記録する。Codexがモデル表面と全身の表示を確認し、色分けの境界や意図とのずれを自己点検する。ver2.0試験の標準はBlenderの材質・プロシージャル表現とし、画像テクスチャ生成、UV、ベイクを使う場合は計画に明示する。単一の色・粗さ指定で模様や布の構造を再現したとは報告しない。

## 7. 最終確認と局所修正

最終確認時に、全身画像だけでなく、部品構成案、資料パック、部品候補、仮組み、材質の各IDと画像・意図を辿れる一覧を提示する。ユーザーは「帽子の背面図から見直す」「帽子の内側を修正」「頭部の位置だけ変える」「帯の色だけ変える」のように工程へ直接指示できる。

修正は変更対象に最も近い工程へ戻り、新しい親計画または既存親計画内の許可済み反復として記録する。元資料・旧候補・過去出力は保持する。資料パックの変更は関連する形状と材質の再点検、形状変更は関連する接続・材質・UV等の再点検、配置だけの変更は全身表示と保持検査を行う。下流候補を黙って上書き・自動採用しない。

`candidate compare` と要件別review、selected / on_hold / rejected、`project set-approved`、selectedの全身候補を対象にした名前付きsource出力は維持する。正式採用前でも試験出力は可能とする。UE、リグ、基本動作は従来どおり段階別の未検証項目として表示する。

## 8. CLIと保存形式の最小変更

`mwb`、Python管理コア、案件単位JSONと不変成果物を維持し、3D実行先をBlenderだけにする。既存案件の暗黙移行や全面的なディレクトリ再編は行わない。

案件フォルダの標準構成は次のとおりとする。`<案件ID>`、`<資料パックID>`、`<実行ID>` 等は完全なUUIDであり、表示名をパスの主キーにしない。フォルダはその種類の記録が初めて作られたときに作成してよい。

```text
projects/<案件ID>/
├─ project.json                     案件索引・要件・部品構成・親子計画・候補・材質・レビュー
├─ references/<参照ID>/             インポートした元画像の不変コピー
├─ artifacts/<候補ID>/              取り込んだ画像・既存メッシュ等の不変コピー
├─ reference-packs/<資料パックID>/    部品別の造形用資料、推定・寸法・出典のmanifest
│  ├─ manifest.json
│  └─ parts/<部品ID>/               必要な方向別画像・構築図
├─ runs/<実行ID>/                    Codex/Blenderの各実行と手修正の取込
│  ├─ plan.json                     実行時点の固定子計画
│  ├─ job.json                      実行主体・入力・操作条件
│  ├─ input-manifest.json           使用ファイルの案件相対パスとhash
│  ├─ action.py                     Blender操作スクリプト。手操作では代わりに操作記録
│  ├─ blender.log                   実行ログ。処理に応じて名称は異なる
│  └─ outputs/
│     ├─ manifest.json             候補ID、成果物のhash、親候補ID
│     ├─ model.blend / model.obj    該当工程で作られるもの
│     ├─ intent.json               造形・配置・材質の意図と推定
│     ├─ checks.json               構造検査とCodexの自己点検
│     └─ previews/                 正面・側面・背面・斜め等
├─ recovery/<チェックポイントID>.json 案件索引更新前の全文チェックポイント
└─ exports/<出力ID>/                選択済み全身候補の名前付きsource出力とmanifest
```

親計画は `project.json` に内容・承認根拠を固定し、実行子計画は従来どおり `runs/<実行ID>/plan.json` にもスナップショットを残す。資料パックは部品ごとの画像を重複作成する義務はなく、既存の `references/` や `artifacts/` の不変ファイルをmanifestの相対パスとhashで参照できる。生成・編集した図面は資料パック内に保存する。`runs` のファイルは工程に応じて存在するものだけを作る。取り込んだ手修正 `.blend` も新しい実行IDにコピーして候補化し、元の作業ファイルや旧候補を上書きしない。

旧案件にある `proposals/`、`inspections/`、`external-runs/` は過去の実験証跡として残し、読み取り時は既存の候補・メモから参照できるようにする。ver2.0の新規実行ではこれらを標準の書き込み先にしない。リポジトリ直下の `experiments/` はハーネス技術試験用で制作案件に含めず、`assets/` は案件へ取り込む前の共通資産である。どちらも `projects/<案件ID>/` の代わりにしない。

- 親計画と資料パックを作成・表示・一覧・承認できる操作を追加する。既存の `generate` / `edit` / `candidate` に、工程・親計画IDで絞る一覧を加える。
- 子計画は親計画と資料パックへの参照、Blender操作と入力・コード・結果hash、自己点検結果を持つ。
- Blenderで制作・手修正した `.blend` と依存ファイルを、親候補付きで正式候補へ登録する操作を加える。すでに登録済みの候補ファイルのhashが変わった場合は問題として記録し、変更を新候補と推定しない。
- 確認用レンダー、Blender原本、OBJ等、材質、実行スクリプト、ログ、検査を同じ `runs/<実行ID>/` の下にまとめる。別の `external-runs` を正規の保存先として増やさない。索引から各実体へ到達できるようにする。
- `project resume`、recoveryチェックポイント、案件全体のバックアップ要件を維持する。過去データは読めるままにし、新形式の項目は新案件・新候補から追加する。

CLIの自然文解釈はCodexが行う。保存・承認・実行・候補登録の正本操作は引き続きCLI経由とし、運用JSONの直接編集を通常フローにしない。

実装の起点はGitの `ver1.0` ブランチ（調査時 `fdecf32`）にあった管理コアとBlenderアダプタである。現行 `ver2.0` ブランチではBlender専用の実行経路を使う。Git対象外の `projects/`・`experiments/` は作業ブランチ切替やコード統合の対象に含めず、保全する。

## 9. ver2.0試験の受け入れ条件

1. 指定した六つの場面だけで通常の一回目の全身候補と最終確認まで到達し、内部の部品・資料・材質をIDから追跡できる。
2. 承認済み親計画と資料パックなしに新規造形が始まらず、範囲外の方法・入力・試行回数を拒否する。
3. 単純部品と少なくとも一つの非単純部品をBlenderで直接制作し、元資料との一致・多方向の見た目・接続・面数・所要時間・修正時間を記録する。
4. 仮組みと材質付与後も部品IDと親候補を追え、ユーザーの手動配置修正または特定工程への指示から派生候補を作れる。
5. 完成度の自己点検に、構造検査、複数方向の画像、資料との差、材質の意図、不明点を含める。ユーザーの最終評価と区別して保存する。
6. 元資料・旧候補・既存出力を保持し、失敗・中断時に原因を読み戻せる。3D処理の実行先はBlenderのみとする。

試験の対象キャラクター、用途、許容面数、造形・材質の合格基準は、その案件の立ち上げと制作計画で決める。技術経路が動いたことだけで、任意のキャラクター品質やUE利用を保証しない。

## 10. 根拠と変更しない事項

- 企画の基準：Notion「企画書 ver0.2｜TripoSRのローカル環境を踏まえたキャラクター部品生成・反復編集ハーネス」。
- フローの基準：Notion「制作フロー ver1.0」「UX仕様書 ver1.1」「操作マニュアル ver1.1」。当初の「仕様書 ver1.0」は設計案として扱う。
- 実験の根拠：Notion「ver1.0実験 メモ」、ver1.0ブランチの実装、現存する `projects/` の試験案件。外部処理結果が `external-runs` と候補索引に分散したこと、表示だけの平滑化と形状平滑化が異なること、仮組みの手動調整が早かったことを反映した。
- UE出力、リグ、基本動作、精密な顔・指、汎用的な部分再生成は本版の実証対象に広げない。
